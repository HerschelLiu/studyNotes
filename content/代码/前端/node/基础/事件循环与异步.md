title: "事件循环与异步"
---

> 前置：会写 JavaScript 的 `Promise` 和 `async/await`。
>
> 目标：能预测一段异步代码的输出顺序，知道什么时候该并发、什么时候会阻塞。

## 1. 为什么需要理解事件循环

Node 是单线程执行 JavaScript 的，但网络、文件、定时器由底层线程池和操作系统完成。事件循环负责：

1. 执行同步代码（调用栈）；
2. 栈空后取出回调执行；
3. 在合适的阶段处理定时器、I/O、`setImmediate` 等。

不理解它，就会出现这些现象：

- 明明写了 `await`，请求还是串行；
- 一个 CPU 密集循环把整个服务卡住；
- `Promise` 回调总是比 `setTimeout(0)` 先执行，却说不清原因。

## 2. 最小示例

```js
console.log('1 script start')

setTimeout(() => console.log('2 timeout'), 0)

Promise.resolve().then(() => console.log('3 promise'))

process.nextTick(() => console.log('4 nextTick'))

setImmediate(() => console.log('5 immediate'))

console.log('6 script end')
```

输出顺序：

```text
1 script start
6 script end
4 nextTick
3 promise
2 timeout
5 immediate
```

记忆要点：

- 同步代码先全部执行；
- `process.nextTick` 优先于 Promise 微任务；
- 微任务清空后才进入事件循环的 timers 阶段；
- `setTimeout(0)` 与 `setImmediate` 的先后在主模块中不保证，在 I/O 回调里 `setImmediate` 通常先执行。

## 3. async/await 只是 Promise 的语法糖

```js
async function getData() {
  const a = await fetchA()
  const b = await fetchB()
  return [a, b]
}
```

上面是**串行**：`fetchB` 要等 `fetchA` 完成。没有依赖时应该并发：

```js
async function getData() {
  const [a, b] = await Promise.all([fetchA(), fetchB()])
  return [a, b]
}
```

需要控制并发数时，不要一次 `Promise.all` 上千个请求：

```js
async function pool(tasks, limit = 5) {
  const results = []
  let index = 0

  const worker = async () => {
    while (index < tasks.length) {
      const current = index++
      results[current] = await tasks[current]()
    }
  }

  await Promise.all(Array.from({ length: limit }, worker))
  return results
}
```

## 4. 错误处理

```js
async function main() {
  try {
    const data = await load()
    console.log(data)
  } catch (error) {
    console.error('加载失败', error)
    process.exitCode = 1
  }
}

main()
```

几个容易忽略的点：

- `await` 的 Promise reject 会以异常形式抛出，必须 `try/catch` 或让调用方处理；
- `Promise.all` 中任意一个 reject，整体立即 reject，其他任务不会取消；
- 忘记处理的 Promise 会触发 `unhandledRejection`，Node 15 之后默认让进程退出：

```js
process.on('unhandledRejection', (reason) => {
  console.error('未处理的 Promise 拒绝', reason)
  process.exit(1)
})
```

## 5. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 接口一个接一个，特别慢 | `await` 写在循环里 | 无依赖时用 `Promise.all` 或并发池 |
| 服务周期性卡顿 | 同步大循环 / 大 JSON 解析占用主线程 | 拆分任务，或放到 `worker_threads` |
| 定时器不准 | 事件循环被长任务占用 | 不要在主线程做 CPU 密集计算 |
| 微任务一直追加，定时器不执行 | 微任务队列饥饿 | 避免在微任务里无限递归 |
| `try/catch` 抓不到回调里的错误 | 错误发生在回调的异步上下文 | 在回调内部处理，或转成 Promise |
| 进程静默退出 | 未处理的 rejection / 未捕获异常 | 监听 `unhandledRejection`、`uncaughtException` |

## 6. 项目里怎么用

- 批量下载、批量请求：用并发池限制同时进行的数量；
- 启动脚本里做资源初始化：`await` 后再 `listen`，避免请求进来时数据库还没连上；
- 关闭服务：监听 `SIGTERM`，停止接收新请求，等待进行中的任务结束（见[进程、线程与子进程](./进程、线程与子进程.md)）。

## 7. 练习

1. 写一个脚本，验证 `nextTick`、`Promise.then`、`setTimeout`、`setImmediate` 的顺序；
2. 用并发池下载 20 个 URL，限制并发为 3，记录总耗时；
3. 写一个阻塞 3 秒的 `while` 循环，用另一个定时器观察它是否被延迟；
4. 把一段回调风格的 `fs.readFile` 改写成 `fs/promises` + `async/await`。
