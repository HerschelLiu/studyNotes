> 基于 `@file-viewer/vue3` + **按需装配 renderer** 的文件预览组件：一份 `url`（字符串 / `Blob` / `ArrayBuffer`）自动识别类型并渲染，图片走 Element Plus，PDF / Word / Excel 交给 file-viewer（PPT 主动不支持，回退 iframe），未装配的扩展名回退浏览器 iframe；`v-model` 控制抽屉显隐，`mode` 切换「抽屉 / 页面内联」两种外壳。
>
> 源码位置：`src/components/Preview/`（minyi_vue3）。本文按 **新项目从零接入** 的顺序编写：先装依赖 → 配 Vite → 拷组件 → 补外部依赖 → 验证 → 使用 → 新增格式 → 查问题 → 应急回退。

**5 分钟接入清单**（详细步骤见下文）：

1. 装依赖：`npm i @file-viewer/vue3 @file-viewer/core @file-viewer/doc @file-viewer/renderer-pdf @file-viewer/renderer-word @file-viewer/renderer-spreadsheet @file-viewer/renderer-image file-type @vueuse/core element-plus`；`npm i -D @file-viewer/vite-plugin sass`
2. 配 Vite：`fileViewerRenderers({ renderers: ['pdf', 'word', 'spreadsheet', 'image'], copyAssets: { baseDir: 'file-viewer' } })`
3. 复制 `src/components/Preview/`（5 个文件）
4. 处理外部依赖：`CompDrawer`、`useTempRefs`、`useCalcHeight`、`useError`（都有可替换的简化写法）
5. 页面里使用：`<CompPreview v-model="show" :url="url" />`

## 概述

- **入口组件** `Preview/index.vue`：
  - `mode="drawer"`（默认）：`v-model` 控制抽屉；图片且 `imageViewer="element"` 时不打开抽屉，直接用 `el-image-viewer` 全屏查看。
  - `mode="page"`：直接在当前页面内联渲染，不需要 `v-model`。
- **类型判定与渲染分工**：
  - 图片（`imageViewer="element"`）→ `el-image`（抽屉模式为 `el-image-viewer`）。
  - 项目**已装配**的 38 个扩展名（PDF / Word / Excel / 图片）→ `FileViewer`（`@file-viewer/vue3`）。
  - 其余扩展名 → 浏览器原生 `iframe`；浏览器打不开时为空白或直接下载。
- **按需装配**：`@file-viewer/vue3` 只是组件壳，格式能力来自 `@file-viewer/renderer-*` 包。`vite/plugins/file-viewer.ts` 声明装配哪些能力，`usePreview.ts` 的 `FILE_VIEWER_RENDERER_IDS` 必须同步同一份清单；未装配的格式不会进入 bundle（见 [新增格式支持](#新增格式支持)）。
- **地址解析可插拔**：组件**不内置** MinIO / OSS / COS 地址换取。需要时通过 `resolveUrl` 传入解析函数（同步或异步），不传则原样使用 `url`，解析失败也回退原地址。
- **文件名可覆盖**：`fileName` 属性透传给 file-viewer 作为下载 / 导出名，MinIO、OSS 这类 UUID 地址不会再下载成乱码文件名；未带扩展名时按识别出的类型自动补全（`合同` → `合同.pdf`）。
- **下载 / 缩放 / 导出 / 检索**：直接使用 file-viewer 内置工具栏，不在组件内重复实现（遵循 `AGENTS.md` 15.1「内置能力优先」）。
- **打印**：默认使用自定义「打印」按钮——把 file-viewer **已渲染**的 HTML 打进隐藏 iframe 打印，不经过 `window.open`，不会被弹窗拦截；也可切换为 file-viewer 内置打印菜单。
- **.doc 颜色补丁**：二进制 `.doc` 的自定义字体颜色（`sprmCCv`）在 file-viewer 中会退化成灰色，`msDocColors.ts` 在渲染完成后按文本顺序回填颜色（官方无配置项、无流行替代方案，故保留补丁）。
- **零业务侵入**：组件只依赖 Vue / Element Plus / VueUse / file-viewer，不依赖 vue-query、axios、Pinia、路由或若依工具函数，可整目录搬到任意 Vue 3 项目。

## 为什么改按需装配（体积与启动）

`@file-viewer/vue3-full` = `@file-viewer/vue3` + `@file-viewer/preset-all` + `file-viewer-copy-assets`，一次装齐 275 个扩展名的渲染链路。它在本项目里的实际代价：

| 指标 | `vue3-full`（改造前） | `vue3` + 4 个 renderer（当前） |
| --- | --- | --- |
| 打包产物 | ≈ 90 MB（压缩后） | ≈ 37 MB（压缩后，去掉 PPT 前实测） |
| 首次启动资源复制 | ≈ 200 MB → `public/file-viewer/` | ≈ 12 MB → `public/file-viewer/` |
| dev 依赖图 | PDF / Office / CAD / 3D / Typst / 压缩包 / 工程格式全量 | 只有 PDF / Word / Excel / 图片 |
| 新增一种格式 | 已全量，无法再裁 | 装一个 renderer 包 + 加一个 renderer id |
| 组件入口 | `import { FileViewer } from '@file-viewer/vue3-full'` | `import { FileViewer } from '@file-viewer/vue3'` |

> 改造前（vue-office 时代）产物约 0.9 MB，所以 0.9 MB → 90 MB 的跳变几乎全部来自全量 file-viewer 的运行时与资源；按需装配后回落到 37 MB。本轮再去掉 PPT 的 presentation 链路（`pptx` 引擎 + 旧 `.ppt` 运行时），资源和渲染 chunk 还会各自再少一截，准确数字以 `du -sh dist` 实测为准。

原理：3.x 把重渲染链路拆成独立的 `@file-viewer/renderer-*` 包，`@file-viewer/vue3` 只依赖 `@file-viewer/core`。Vite 插件读取声明的 renderer，生成虚拟模块按需 `import()`，**只有被装配的包才会进 bundle**；`copyAssets` 也只复制这些包对应的 Worker / WASM / 字体。所以「少装一个 renderer」会同时减少安装体积、构建产物体积和 dev 启动耗时。

启动变慢的三个具体来源（`vue3-full` 时代）：

1. **资源复制**：插件在 dev server 启动时把约 200 MB 资源写进 `public/file-viewer/`，首次全量写、之后逐文件比对；
2. **依赖图**：`preset-all` 把 20+ 个 renderer 及其重依赖（PDF.js、docx、xlsx、three、CAD WASM…）都带进 Vite 的模块图，optimizeDeps / 转换都变重；
3. **public 目录**：`public/` 里多出上万个文件，Vite 监听与拷贝都受影响。

按需装配后这三点同时收敛：只复制 4 条链路的资源、只装配 4 个能力包、`public/file-viewer/` 也只有上千个文件。

> 结论：**不要装 `@file-viewer/vue3-full` / `@file-viewer/preset-all`**，也不要为了「以后可能用到」顺手装 `preset-office`——它会把 PPT、OFD、iWork 等链路一起带回来。

本次改造实际改动的文件：

| 文件 | 改动 |
| --- | --- |
| `package.json` | 移除 `@file-viewer/vue3-full`，新增 `@file-viewer/vue3` + 4 个 `renderer-*`（pdf / word / spreadsheet / image） |
| `vite/plugins/file-viewer.ts` | 声明 4 个能力；`copyAssets: { baseDir: 'file-viewer' }` 固定资源目录 |
| `previewItem.vue` | `import { FileViewer } from '@file-viewer/vue3-full'` → `@file-viewer/vue3` |
| `usePreview.ts` | 从 `DEFAULT_SUPPORTED_EXTENSIONS`（275）改为按 `FILE_VIEWER_RENDERER_IDS` 过滤（38） |
| `public/file-viewer/` + `.gitignore` | 切换后清空一次并重新生成；该目录仍走 gitignore |

## 已装配能力（支持格式）

本项目只预览 **PDF / 图片 / Office（Word、Excel）**，`vite/plugins/file-viewer.ts` 声明 4 条能力、7 个 renderer，共覆盖 **38** 个扩展名。`usePreview.ts` 的 `FILE_VIEWER_RENDERER_IDS` 与这张表一一对应：

| 能力 id | renderer id | 扩展名 |
| --- | --- | --- |
| `pdf` | `pdf` | `pdf` |
| `word` | `office-word-openxml` | `docx` `docm` `dotx` `dotm` |
| `word` | `office-word-binary` | `doc` `dot` |
| `word` | `open-document` | `rtf` `odt` `odp` |
| `spreadsheet` | `spreadsheet-openxml` | `xlsx` `xltx` `xlsm` `xlsb` `xls` `xlt` `xla` `xlam` `xltm` `csv` `tsv` `ods` `fods` |
| `spreadsheet` | `spreadsheet-dbf` | `dbf` |
| `image` | `image` | `gif` `jpg` `jpeg` `bmp` `tiff` `tif` `png` `svg` `webp` `avif` `ico` `heic` `heif` `jxl` |

说明：

- **PPT 已明确不支持**：`pptx` `pptm` `potx` `potm` `ppsx` `ppsm` `ppt` `pot` 都不在装配范围，统一回退浏览器 `iframe`（浏览器打不开时表现为空白或下载）。这是产品确认过的取舍，不是漏配；要恢复见 [新增格式支持](#新增格式支持) 里的 PPT 行。
- **图片默认不走 file-viewer**：`imageViewer="element"`（默认）时由 `el-image` 渲染；只有 `imageViewer="file-viewer"` 才交给 `image` renderer（可用工具栏 / 缩放 / 旋转，`tiff`、`heic` 等多页或特殊格式也靠它）。
- **38 个扩展名以外 → `iframe`**：`txt`、`md`、`zip`、`ofd`、`dwg`、`mp4`、`xmind`…… 目前都交给浏览器。能在浏览器里直接打开的仍可正常显示，打不开的表现为空白或下载，属预期。
- **`rtf` 是半支持**：`open-document` 覆盖 `rtf`，但官方把 RTF 解析列为可选能力，需另装 `@file-viewer/capability-rtf` 并副作用引入；不装时打开 `.rtf` 会提示启用命令。详见 [新增格式支持](#新增格式支持)。
- **两种「不支持」要区分**：
  1. 不在 38 个扩展名内 → 组件判成 `iframe`，不报错；
  2. 在 file-viewer 的 275 个矩阵内、但项目没装对应 renderer（如 `ofd`、`zip`、`dwg`、`pptx`）→ 如果把扩展名加进白名单却没装包，会进入「需要装配预览能力」空态，而不是 iframe。
- 38 个扩展名来自 `@file-viewer/core` 的 `DEFAULT_RENDERER_DEFINITIONS` 按 renderer id 过滤，升级 `@file-viewer/core` 后列表可能变大，但**不会自动新增能力**，仍需装包 + 改配置。

## 新项目安装

### 1. 安装依赖

参考环境（minyi_vue3）：Vue `3.5.26`、Element Plus `2.13.1`、`@vueuse/core` `14.1.0`、Vite `6.4.1`、Node `v24.20.0`。

最低要求：

| 依赖 | 版本要求 | 原因 |
| --- | --- | --- |
| `vue` | **≥ 3.5** | 使用了 `useTemplateRef`（3.5）与 `defineModel`（3.4 起稳定） |
| `element-plus` | ≥ 2.4 | `el-image` / `el-image-viewer` / `v-loading` / `el-drawer` |
| `@vueuse/core` | ≥ 10 | `useAsyncState` / `useObjectUrl` |
| `vite` | ≥ 5 | `@file-viewer/vite-plugin` 的挂载方式 |
| Node.js | ≥ 20 | Vite 6 要求 |
| `sass` | 任意 1.x | 组件 `<style lang="scss">` |

```bash
# 运行时依赖：组件壳 + 4 个按需 renderer（版本全部对齐 3.3.x）
npm i @file-viewer/vue3@3.3.3 @file-viewer/core@3.3.3 @file-viewer/doc@3.3.3 \
      @file-viewer/renderer-pdf@3.3.3 @file-viewer/renderer-word@3.3.3 \
      @file-viewer/renderer-spreadsheet@3.3.3 @file-viewer/renderer-image@3.3.3 \
      file-type @vueuse/core element-plus

# 构建期依赖
npm i -D @file-viewer/vite-plugin@3.3.3 sass
```

各包职责：

| 包 | 用途 | 是否必须 |
| --- | --- | --- |
| `@file-viewer/vue3` | 组件壳，只依赖 `core`，**本身不带任何格式能力** | **必须** |
| `@file-viewer/core` | 直接 `import type` 类型，以及 `DEFAULT_RENDERER_DEFINITIONS` / `IMAGE_EXTENSIONS` 常量 | **必须**（代码里直接 import） |
| `@file-viewer/renderer-pdf` | PDF（PDF.js） | **必须**（`usePreview` 白名单含 `pdf`） |
| `@file-viewer/renderer-word` | `docx` / `doc` / `odt` / `odp` / `rtf` | **必须**（白名单含 3 个 id） |
| `@file-viewer/renderer-spreadsheet` | `xlsx` / `xls` / `csv` / `ods` / `dbf` | **必须** |
| `@file-viewer/renderer-image` | `tiff` / `heic` / `jxl` 等；默认图片仍由 Element 渲染 | **必须**（白名单含 `image`） |
| `@file-viewer/doc` | `msDocColors.ts` 解析二进制 `.doc` | 复制了 `msDocColors.ts` 就必须 |
| `file-type` | 二进制源 MIME 不可用时按文件头识别真实类型（动态 `import()`，不占首屏） | 需要二进制预览就必须 |
| `@file-viewer/vite-plugin` | 生成 renderer 虚拟模块、复制 Worker / WASM / 字体、注入 chunk 分组 | **必须**，否则 PDF 等格式缺运行时资源 |
| `@file-viewer/vue3-full` | 全量包（会自动带上 `preset-all`） | **不要装** |
| `@file-viewer/renderer-presentation` / `-pptx` / `-ppt` | PPT 渲染链路 | **不要装**（产品已确认不预览 PPT） |

注意事项：

- **版本必须对齐**：`vue3` / `core` / `doc` / 所有 `renderer-*` / `vite-plugin` 保持同一个 `3.3.x` 版本，混用会报资产版本不一致。
- **不要装 preset**：`preset-office` 会带 `presentation`（PPT 直接回来）+ `ofd` + `iwork` + `hangul` + `wordperfect`，而且**不含 `image`**；`preset-standard` 也含 `renderer-pptx`。要保住「不含 PPT」这个裁剪结果，只能按上面的 4 个包手选。
- **`@file-viewer/vue3` 现在是直接依赖**：`previewItem.vue` 里的 `import '@file-viewer/vue3/dist/vue3.css'` 可直接解析，pnpm 严格模式也不再需要 `public-hoist-pattern`。
- **`file-type` 的 Node 版本**：本项目用 22.x，`engines` 要求 Node ≥22；它只在浏览器端动态加载，但构建机版本过低时 npm 会报 `EBADENGINE`（`engine-strict` 下直接失败）。构建机较旧时可退到仍提供 `fileTypeFromBlob` / `fileTypeFromBuffer` 的 19.x，代码无需改。
- 体积提示：当前 4 条链路的资源约 **12 MB**（`public/file-viewer/`，不入库）；构建产物 ≈ **37 MB**（压缩后，去 PPT 前实测，去掉 presentation 后还会更小）。从 `vue3-full` 切过来时，`public/file-viewer/` 里仍留着全量旧资源，需要清空一次（见下一节）。

### 2. 配置 Vite：声明 renderer + 发布资源

file-viewer 的 PDF Worker、Office 解析 Worker、字体等不在 JS bundle 里，必须由 Vite 插件复制到部署目录，否则这些格式会白屏或报 Worker 404。

项目里的实际配置（`vite/plugins/file-viewer.ts`）：

```ts
import { fileViewerRenderers } from '@file-viewer/vite-plugin'

/**
 * 项目只预览 PDF / 图片 / Office（Word、Excel），只装配对应 renderer。
 * 使用 @file-viewer/vue3-full / preset-all 会把 30+ 条渲染链路和 200MB+ 资源一起装进来，
 * 导致开发启动变慢、构建产物膨胀，因此这里改为标准包 + 按需 renderer。
 * PPT（.ppt / .pot / .pptx）已确认不需要预览，不再装配 presentation renderer。
 * 新增预览类型时，同时补充本数组与 package.json 中对应的 renderer / assets 包。
 */
const FILE_VIEWER_RENDERERS: readonly string[] = ['pdf', 'word', 'spreadsheet', 'image']

/**
 * file-viewer 渲染器资源：只把所有已装配 renderer 的 Worker / WASM / 字体复制到
 * public/file-viewer（构建后为 dist/file-viewer），与运行时默认资源基址 `/file-viewer/` 一致。
 */
export default function createFileViewer() {
  return fileViewerRenderers({
    renderers: FILE_VIEWER_RENDERERS,
    copyAssets: { baseDir: 'file-viewer' }
  })
}
```

> `chunkStrategy` 不用写：插件默认就是 `'renderer'`（按 renderer 拆 chunk）。

`renderers` 用的是**能力 id**（`renderer-` 后面的名字，如 `renderer-word` → `word`），一条能力可能注册多个 renderer id：

| 能力 id | 自动注册的 renderer |
| --- | --- |
| `pdf` | `pdf` |
| `word` | `office-word-openxml`、`office-word-binary`、`open-document` |
| `spreadsheet` | `spreadsheet-openxml`、`spreadsheet-dbf` |
| `image` | `image` |

只想保留某条能力里的单个格式（例如只要 `docx`、不要 `doc`）时，改用扩展名声明：

```ts
fileViewerRenderers({
  formats: ['pdf', 'docx', 'xlsx'], // 插件按扩展名反查 renderer 包
  copyAssets: { baseDir: 'file-viewer' }
})
```

挂到 `vite/plugins/index.ts` 的插件数组里（省略的 import 与项目其他插件保持一致）：

```ts
import createFileViewer from './file-viewer'

export default function createVitePlugins(viteEnv: Record<string, string>, isBuild = false) {
  const vitePlugins: PluginOption[] = [
    vue({
      script: {
        // Vue 3.3 需要显式开启 defineModel；3.4+ 默认开启，保留无副作用
        defineModel: true
      }
    })
    // ... 其他插件
  ]

  vitePlugins.push(createFileViewer())

  return vitePlugins
}
```

如果项目没有拆插件目录，直接内联：

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import { fileViewerRenderers } from '@file-viewer/vite-plugin'

export default defineConfig({
  plugins: [
    fileViewerRenderers({
      renderers: ['pdf', 'word', 'spreadsheet', 'image'],
      copyAssets: { baseDir: 'file-viewer' }
    })
  ]
})
```

`copyAssets` 的行为：

| 阶段 | 输出位置 | 说明 |
| --- | --- | --- |
| `vite dev` | `public/file-viewer/` | 只复制已装配 renderer 的资源，本项目约 12 MB；后续启动逐文件比对，内容一致则跳过写入 |
| `vite build` | `dist/file-viewer/` | 构建产物的一部分，**必须随站点一起部署** |
| 部署路径 | `<base>/file-viewer/` | 根路径部署即 `/file-viewer/`；子路径部署（如 `/admin/`）即 `/admin/file-viewer/` |
| 控制台 | `[file-viewer:vite-plugin] Copied x/y renderer assets to ...` | 每次 dev 启动 / build 打印，用来确认复制结果 |

`baseDir` 的作用（本项目显式写 `'file-viewer'`）：

- 不写时，插件在**没装 full 包**的情况下默认 `baseDir` 为空，资源会复制到站点根的 `vendor/`；装了 `@file-viewer/*-full` 才默认用 `file-viewer/`。
- 写了 `baseDir` 后，插件同时通过虚拟模块调用 `setDefaultFileViewerAssetBaseUrl('/file-viewer/')`，**复制目录与运行时基址一起对齐**，不需要手动改代码。
- 本项目写它，是为了沿用原来的部署路径 `<base>/file-viewer/`，Nginx 与历史部署脚本不用改；想放到根目录也可以不写，插件会自动把运行时基址设成根。
- 以后如果手动改 `baseDir`，运行时基址会跟着变；不要再额外调用 `setDefaultFileViewerAssetBaseUrl()` 写死旧路径，否则两边不一致就会 404。

配套 `.gitignore`：

```text
# @file-viewer/vite-plugin 复制生成的渲染器资源
public/file-viewer/
```

清理旧资源（从 `vue3-full` 切过来时只做一次）：

```bash
rm -rf public/file-viewer node_modules/.vite
npm run dev   # 控制台出现 Copied x/y，public/file-viewer 只保留 4 条链路的资源
```

> 插件只写入「本次声明的 renderer 需要的文件」，不会清理目录里已存在但这次不再需要的文件；不清空就会把 full 时代的 PPT / CAD / 3D 等资源继续留在 `public/`，既占仓库又会被打进 `dist`。

> `inject` 默认为 `true`，插件会自动把虚拟模块注入 HTML 入口，`@file-viewer/vue3` 的 `autoRenderers` 默认读取它，因此业务代码**不需要**手动 import renderer，也不需要 import `virtual:file-viewer-renderers`。

#### 4.2 useTempRefs

`previewItem.vue` 里只有一句：

等价替换（Vue 3.5）：

#### 4.3 useCalcHeight

`previewItem.vue` 用 `useCalcHeight` 把预览区高度算成「视口剩余高度」：

```ts

  enabled: computed(() => previewType.value !== 'image'),
  observeGap: false,
  bottomOffset: 16,
  minHeight: '60vh',

```

`iframe` / `FileViewer` 的高度是 `100%`，父容器没有高度就会塌成 0，所以这一段不能直接删。

- **方案 A**：复制 `src/hooks/useCalcHeight.ts`（依赖 `@vueuse/core` 的 `useWindowSize` / `useResizeObserver` / `useRafFn`）。
- **方案 B**：不需要「自适应视口」时，给容器一个固定高度，删掉 `useCalcHeight` 与 `contentStyle`，并移除 `file` / `iframe` 两个分支上的 `:style="contentStyle"`：

```vue
<div
  v-else-if="previewType === 'file'"
  ref="viewerRef"
  class="preview-content">
```

```scss
.preview-content {
  height: 70vh; // 或 calc(100vh - 120px)
  overflow: auto;
}
```

1. `npm run dev` 启动后，控制台应出现 `[file-viewer:vite-plugin] Copied x/y renderer assets to ...`，`public/file-viewer/` 下应能看到 `vendor/pdf/`、`vendor/docx/`、`vendor/xlsx/`，且**没有** `vendor/pptx`、`vendor/ppt`。
2. 新建一个临时页面放一个 PDF：正常应出现 file-viewer 工具栏、页码、缩放。

```vue

<template>
  <CompPreview v-model="show" :url="pdfUrl" />
</template>

<script lang="ts" setup>
  import CompPreview from '@/components/Preview/index.vue'

</script>
```

3. 打开浏览器 Network，筛选 `file-viewer`：PDF 应加载 `/file-viewer/vendor/pdf/pdf.worker.mjs`、`/file-viewer/vendor/pdf/cmaps/...`、`/file-viewer/vendor/pdf/fonts/...`，而不是 404。
4. 再测 `docx`、`xlsx`、`png`（图片走 Element，不应出现 file-viewer 工具栏）。
5. 测 `pptx` / `ppt`：应**回退 iframe**（空白或下载），不应出现 file-viewer 工具栏——这是去掉 PPT 渲染后的预期行为。

## 使用示例

### 抽屉模式（默认）

最常用：列表页点「预览」，传文件地址，`v-model` 控制显隐。

```vue
<template>
  <el-button @click="handlePreview(row)">预览</el-button>

  <CompPreview
    v-model="showPreview"
    :url="previewUrl"
    :resolve-url="resolvePreviewUrl" />
</template>

<script lang="ts" setup>
  import { readProfileUpload } from '@/api/basic/common'

  import CompPreview from '@/components/Preview/index.vue'

  const showPreview = ref(false)
  const previewUrl = ref('')

  /** MinIO relativePath → 可访问地址；必须保持函数引用稳定 */
  const resolvePreviewUrl = async (url: string) => (await readProfileUpload(url)).url

  const handlePreview = (row: { relativePath: string }) => {
    previewUrl.value = row.relativePath
    showPreview.value = true
  }
</script>
```

行为要点：

- 图片（`jpg/png/...`）：不打开抽屉，直接全屏 `el-image-viewer`；关闭即 `show = false`。
- 其他格式：打开抽屉，内容区由 `CompDrawer` 的 `el-scrollbar` 滚动。
- 抽屉默认 `destroy-on-close`，关闭即销毁预览实例；再次打开会重新加载。

### 页面内联模式

不做弹层，直接把预览嵌在页面里（如详情页的附件区）：

```vue
<template>
  <div class="attachment-preview">
    <CompPreview
      mode="page"
      :url="fileUrl" />
  </div>
</template>

<script lang="ts" setup>
  import CompPreview from '@/components/Preview/index.vue'

  defineProps<{ fileUrl: string }>()
</script>
```

注意：

- `mode="page"` 不使用 `v-model`，`url` 为空时什么都不渲染。
- 若 `fileUrl` 是 MinIO / OSS 的 `relativePath`，再补 `:resolve-url`（写法同抽屉模式）。
- 高度由 `useCalcHeight` 计算（`minHeight: 60vh`，扣除页脚 `.copyright` 与 16px 间隙）；如果页面没有 `.copyright` 页脚，把 `previewItem.vue` 里的 `footerSelector` 改成项目实际页脚选择器，或走 [4.3 的方案 B](#43-usecalcheight)。

### 直链地址

地址本身可以直接访问（后端直出、CDN、公开桶）时，不传 `resolveUrl`：

```vue
<CompPreview v-model="show" :url="'https://cdn.example.com/demo.pdf'" />
```

组件会把字符串原样交给 file-viewer / iframe；只有 `resolveUrl` 存在时才走解析。

### 自定义下载文件名

MinIO / OSS 的地址末段通常是 UUID（如 `a1b2c3d4-...-9f.pdf`），file-viewer 默认拿它当下载名。传 `fileName` 即可指定业务名称：

```vue
<CompPreview
  v-model="show"
  :url="row.relativePath"
  :file-name="row.name"
  :resolve-url="resolvePreviewUrl" />
```

要点：

- `fileName` 会作为 file-viewer 的 `filename`，影响**下载 / 导出**时的文件名，也会作为二进制源 `File` 的名字（利于 file-viewer 识别类型）。
- 未带扩展名时按识别结果自动补：`fileName="合同"` + PDF → `合同.pdf`；已带正确扩展名则原样使用。
- 只对 `file` 分支生效；图片（Element）和 iframe 分支没有组件内下载入口，文件名无意义。
- 它只改「名字」，不改类型判定：类型仍由 URL 扩展名 / `mime` / 文件头嗅探决定。

### 二进制源：Blob / ArrayBuffer

接口返回文件流、上传前本地预览等场景，直接传 `Blob` / `ArrayBuffer`：

```ts
const show = ref(false)
const source = ref<Blob | ArrayBuffer>()
const mime = ref('')

/** 接口返回 Blob */
const previewBlob = (blob: Blob) => {
  source.value = blob
  mime.value = blob.type // 如 application/pdf
  show.value = true
}

/** 接口返回 ArrayBuffer：建议给 mime；不给时会按文件头嗅探兜底 */
const previewBuffer = async (buffer: ArrayBuffer) => {
  source.value = buffer
  mime.value = 'application/vnd.openxmlformats-officedocument.wordprocessingml.document' // docx
  show.value = true
}
```

```vue
<CompPreview v-model="show" :url="source" :mime="mime" />
```

行为要点：

- **MIME 优先级**：`mime` 属性 > `Blob.type`。两者都会先去参数、转小写（`application/pdf;charset=UTF-8` → `application/pdf`），再查 `MIME_EXT_MAP`。
- **`file-type` 嗅探兜底**：MIME 缺失 / 是 `application/octet-stream` / 映射不到时，动态 `import('file-type')` 按文件头识别（默认取样约 4 KB），再用 `MIME_EXT_MAP` 换算扩展名。能落到 `file` / `image` 分支的有 `pdf`、`docx`、`xlsx`、`png`、`jpg`、`gif`、`webp`、`bmp`；旧版 `.doc` / `.xls` / `.ppt` 这类 OLE 复合文档只会被识别成 `application/x-cfb`（表里没有），仍需显式传 `mime`；`svg` 是文本格式，也不识别。
- **嗅探期间不生成 blob 地址**：Safari 会把 MIME 不明的 blob 当下载处理，所以先等识别结果；这段时间 `image` / `iframe` 分支不渲染（`browserUrl` 为空），属于短暂等待而不是卡死。
- **仍识别不出 → `iframe`**：`ext` 为空时走浏览器，通常表现为空白或下载。`file-type` 能识别但 `MIME_EXT_MAP` 没收录的类型（如 `tiff`、`heic`、`zip`、`mp4`、`cfb`）也会落到这里；`pptx` 虽能识别，但 PPT 渲染已去掉，同样走 `iframe`。
- 图片 / iframe 分支：内部用 `useObjectUrl` 把二进制转 object URL，组件卸载、源变化或嗅探未完成时不创建；完成后自动 `revokeObjectURL`。
- file-viewer 分支：内部把二进制包成带文件名的 `File`（优先 `fileName`，否则 `预览文件.<ext>`），因为 file-viewer 依赖文件名识别类型。
- 下载按钮由 file-viewer 自带，文件名优先级：`fileName` > `url` 末段 > `预览文件.<ext>`。

### 对象存储：MinIO / OSS / COS

组件**不内置**地址换取，约定由消费方通过 `resolveUrl` 提供：

```ts
/** 同步拼签名地址（二选一） */
const resolveUrl = (url: string) => `${ossBase}/${url}?sign=${getSign(url)}`

/** 异步换取，项目里的写法（二选一） */
const resolvePreviewUrl = async (url: string) => (await readProfileUpload(url)).url
```

```vue
<CompPreview v-model="show" :url="previewUrl" :resolve-url="resolveUrl" />
```

要点：

- 支持同步返回 `string` 或返回 `Promise<string>`。
- 解析抛错 / 返回空串时**回退原始地址**，由浏览器或预览器自己报错，组件不会白屏。
- **函数必须是稳定引用**：`resolveUrl` 是 `watch` 的依赖，写成模板内联箭头函数（`:resolve-url="(u) => readProfileUpload(u)"`）会导致每次渲染都重新解析、重复请求。请定义在 `setup` 顶层（或写进 `const` 模块级函数）。
- 需要刷新签名时：同一个字符串重复赋值不会触发重新解析；可以先把 `url` 置空再赋新值，或让 `url` 本身带上时间戳/签名。

### 工具栏定制

`toolbar` 透传 file-viewer 的 `FileViewerToolbarOptions`，默认值：

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `download` | `true` | 下载 |
| `zoom` | `true` | 缩放 |
| `search` | `false` | 文档内检索 |
| `theme` | `false` | 明暗主题切换 |
| `exportHtml` | `false` | 导出 HTML |
| `print` | 由 `useBuiltinPrint` 决定 | 传 `toolbar.print` 无效 |

```vue
<CompPreview
  v-model="show"
  :url="previewUrl"
  :toolbar="{ download: false, search: true, theme: true }" />
```

还支持 `order` / `items` / `permissions` / `position` / `beforeDownload` / `beforePrint` 等 file-viewer 原生配置，直接透传，语义见 [@file-viewer/core 类型](https://doc.file-viewer.app/)。下载文件名的来源见 [自定义下载文件名](#自定义下载文件名)。

> 遵守 `AGENTS.md` 15.1：下载 / 缩放 / 导出 / 检索一律用组件内置能力，不要在业务层重复写按钮。

### 打印

默认（`showPrint: true`、`useBuiltinPrint: false`）：

- file-viewer 工具栏右侧出现「打印」按钮；
- 点击调用 `api.printRenderedHtml({ printWindow })`，把**已渲染**的 HTML 写进常驻隐藏 iframe 再打印；
- 不使用 `window.open`，避免被浏览器拦截，也不会新开页面；
- 仅在 `availability.print` 为 `true` 时显示（如纯图片、压缩包等没有可打印内容时自动隐藏）；
- 打印失败会把预览切到错误态，组件用 `viewerKey` 重新挂载并 `ElMessage` 提示，不影响继续使用。

需要 file-viewer 内置打印菜单（支持「遮盖敏感信息后再打印」等）：

```vue
<CompPreview
  v-model="show"
  :url="previewUrl"
  use-builtin-print />
```

不需要打印按钮：

```vue
<CompPreview
  v-model="show"
  :url="previewUrl"
  :show-print="false" />
```

### 全局注册（可选）

## 内部机制

### 预览类型判定

```text
ext 来源（按优先级）
  ├─ string 源 ─────────────> 地址末段（去 query）
  └─ 二进制源 ──┬─ mime（去参数、小写）命中 MIME_EXT_MAP
                ├─ Blob.type 命中 MIME_EXT_MAP
                └─ file-type 嗅探（动态 import）：pdf / docx / xlsx / png / jpg / gif / webp / bmp
        │
        ├─ imageViewer === 'element' 且 ext ∈ IMAGE_EXTENSIONS(14) ──> 'image'  → el-image / el-image-viewer
        ├─ ext ∈ 已装配 renderer 的扩展名(38) ───────────────────────> 'file'   → FileViewer
        └─ 其他 ─────────────────────────────────────────────────────> 'iframe' → <iframe :src="browserUrl">
```

代码位置：`usePreview.ts` 的 `ext` / `previewType`。

关键实现（与旧版不同）：

```ts
/** 去掉 MIME 参数并统一小写 */
const normalizeMime = (value?: string) => value?.split(';')[0].trim().toLowerCase() ?? ''

/** 二进制源：mime 优先，其次 Blob.type */
const candidates = [mime, source instanceof Blob ? source.type : undefined]
const type = candidates.map(normalizeMime).find(value => MIME_EXT_MAP[value])

/** 都识别不到时，动态 import file-type 按文件头嗅探 */
const sniffedExt = ref('')
const ext = computed(() => mimeExt.value || sniffedExt.value)
```

- 旧版用的是 `DEFAULT_SUPPORTED_EXTENSIONS`（core 全量 275 个）。按需装配后必须换成上面的过滤写法，否则没装 renderer 的扩展名也会被判成 `file`，进入「需要装配预览能力」空态。
- **两份清单一改一起改**：`FILE_VIEWER_RENDERER_IDS` 与 Vite 插件声明的 `renderers`（或 `formats`）必须同源，否则表现为「白屏 / 空态 / 明明装了包却走 iframe」。
- **嗅探只做兜底**：由 `file-type` 按文件头识别，实际能落到 `file` / `image` 分支的是 PDF、docx / xlsx、PNG / JPEG / GIF / WebP / BMP；OLE 复合文档（旧 `.doc` / `.xls` / `.ppt`）只识别为 `application/x-cfb`，`MIME_EXT_MAP` 里没有，SVG 这类文本格式也不识别，都仍需显式 `mime`。
- `idx > -1 ? path.slice(idx + 1).toLowerCase() : ''`：字符串地址里没有 `.` 时 `ext` 为空 → `iframe`；因此不带扩展名的下载地址需要调用方保证能直接打开，或改用二进制源 + `mime`。

### 地址解析流程

```text
props.url
  ├─ string ──┬─ resolveUrl 存在 ──> 异步解析 ──> remoteUrl（file-viewer 用）
  │           └─ 不传 / 失败 ─────> 原地址 ────> remoteUrl
  │
  └─ Blob / ArrayBuffer
       ├─ ext：mime > Blob.type > file-type 嗅探（动态 import；异步，丢弃过期结果）
       ├─ 'file'   → sourceFile（File，带文件名 + type）
       └─ 'image'/'iframe' → useObjectUrl(objectBlob)（嗅探完成前不创建）
```

细节：

- `browserUrl`：`string` 时优先用 `resolvedUrl`，解析未完成先用原始地址占位；二进制时用 object URL（嗅探完成前为空）。
- `remoteUrl`：只对字符串源生效，解析完成后才有值；`FileViewer` 收到 `url` 前可能短暂空态。
- `isLoading`：仅表示「远程地址解析中」（`useAsyncState`），**不包含**文件头嗅探；嗅探状态是内部的 `isInspecting`，不对外返回。
- 嗅探用自增 `inspectId` 标记任务，源或 `mime` 变化后过期结果会被丢弃；`useAsyncState(..., { resetOnExecute: true })` 同样会丢弃过期的地址解析结果，无需手写竞态标记。

### 文件名解析

`usePreview.ts` 的 `fileName` 计算优先级：

```text
props.fileName（业务名）
  ├─ 未带 .ext ──> 追加识别出的扩展名：合同 → 合同.pdf
  └─ 已带 .ext ──> 原样使用
string 源 ──> url 末段（decodeURIComponent）
其他 ──────> 预览文件.<ext>（无 ext 时 预览文件）
```

- 由 `index.vue` 透传给 `PreviewItem`，最终作为 `FileViewer` 的 `filename`，同时用于二进制源 `new File(...)` 的名字。
- 扩展名来自同一套识别结果（URL / `mime` / 文件头嗅探），所以是「先定类型、再补名字」。
- 如果传入名字带的是**错误**扩展名（实际 PDF 却传 `x.docx`），会再追加成 `x.docx.pdf`；调用方保证后缀正确即可。
- `fileName` 只影响展示 / 下载名，不参与 `previewType` 判定。

### 高度计算

`previewItem.vue`：

```ts
const { height } = useCalcHeight(viewerRef, {
  enabled: computed(() => previewType.value !== 'image'),
  observeGap: false,
  bottomOffset: 16,
  minHeight: '60vh',
  footerSelector: '.copyright'
})
```

- 只有 `file` / `iframe` 分支需要高度（`FileViewer` 与 `iframe` 都是 `height: 100%`）。
- 计算方式：`window.innerHeight - rect.top - 页脚高度 - 16`，且不小于 `60vh`；抽屉/弹窗内会自动跳过页脚（`.el-overlay` 判断）。
- `observeGap: false`：预览在抽屉里没有下方兄弟元素，不需要累加间隙。
- 视口 resize、父容器尺寸变化、`v-if` 重新挂载都会自动重算（`useResizeObserver` + `useRafFn`）。

### 打印实现

`previewItem.vue`：

1. `ensurePrintWindow()` 复用常驻隐藏 iframe（`position:fixed;width:0;height:0`，**不能用 `display:none`**，否则部分浏览器不渲染内容导致 `print()` 无效）。
2. 同步写入标准模式空文档（`<!doctype html>...`），跳过库内对 `about:blank` 的兼容修复，避免初始化超时。
3. 调用 `api.printRenderedHtml({ printWindow })`，由 file-viewer 把当前渲染结果注入该窗口并触发打印。
4. 打印中 `isPrinting` 置位防重入；失败时 `useError(message)` + `viewerKey++` 重新挂载预览（file-viewer 打印失败会把自身切到错误态）。
5. `onBeforeUnmount` 移除 iframe。

### .doc 颜色补丁

`msDocColors.ts`：

- **问题**：二进制 `.doc` 的字符自定义颜色存在 `sprmCCv`（`sprm_6870`）里，file-viewer 的 msdoc 渲染只读 16 色调色板，自定义 RGB 会退化成灰色。
- **官方方案**：无。`MsDocRenderOptions` 只有 `css` / `reviewMode` / `externalLinkPolicy` / `externalResourcePolicy`，没有颜色映射或调色板扩展配置。
- **流行方案**：无。浏览器端没有其他能渲染二进制 `.doc` 的流行 npm 包（`mammoth`、`docx-preview` 只支持 `.docx`）；服务端 LibreOffice 转 PDF 属架构改造。
- **实现**：渲染完成后（`load-complete`）且 `ext === 'doc'` 时，用 `@file-viewer/doc` 的 `parseMsDoc` 重新解析文件，按渲染顺序把颜色回填到 DOM 文本节点上；影子 DOM 递归穿透；失败静默（不影响预览本身）。

代价：`.doc` 会被解析两次（渲染一次 + 补丁一次）。`.docx` 不走补丁。

### 生命周期与资源释放

| 场景 | 行为 |
| --- | --- |
| 抽屉关闭 | `CompDrawer` 默认 `destroy-on-close`，`PreviewItem` 卸载，`printFrame` 移除，object URL 由 `useObjectUrl` 自动释放 |
| `url` 变化 | `useAsyncState` 重置并重新解析（旧结果丢弃）；二进制重新嗅探（旧任务丢弃），object URL 随 `objectBlob` 变化自动释放 |
| `resolveUrl` 变化 | 重新解析当前地址（所以函数引用要稳定） |
| 组件卸载 | `onBeforeUnmount` 移除打印 iframe；`useCalcHeight` 内部 watcher / observer 随作用域销毁 |
| 打印失败 | `viewerKey++` 重新挂载 `FileViewer`，预览从错误态恢复 |

## 新增格式支持

`@file-viewer/vue3` 本身**不含任何格式能力**，格式由 `@file-viewer/renderer-*` 提供。新增一种格式 = 装对应的 renderer 包 + 在 Vite 里声明 + 在 `usePreview.ts` 白名单里加 renderer id，三处缺一不可。

> 最短答案：不是"往 `@file-viewer/vue3` 里装子包"，而是安装与它**平级**的 `@file-viewer/renderer-<格式>`（如 `renderer-ofd`、`renderer-text`、`renderer-archive`），由 Vite 插件自动装配；`@file-viewer/vue3` 只负责组件壳与渲染容器。

官方依据：[按需渲染架构](https://doc.file-viewer.app/zh/guide/on-demand-renderers)、[模块化 Profile 与 Full 兼容边界](https://doc.file-viewer.app/zh/guide/v3-modular-profiles)、[支持格式矩阵](https://doc.file-viewer.app/zh/guide/formats)。

### 四步接入

以「新增 `zip` 压缩包预览」为例：

**① 装包**（版本与现有 3.3.x 对齐）

```bash
npm i @file-viewer/renderer-archive@3.3.3
```

**② Vite 声明能力**

```ts
// vite/plugins/file-viewer.ts
const FILE_VIEWER_RENDERERS: readonly string[] = [
  'pdf',
  'word',
  'spreadsheet',
  'image',
  'archive' // ← 新增
]
```

用 `formats` 声明的项目则加扩展名：`formats: [..., 'zip', 'rar', '7z']`（插件按扩展名反查 renderer 包；缺包时会以 `missingRenderer: 'error'` 中断启动，这是有意的保护）。

**③ 白名单加 renderer id**（最容易漏的一步）

```ts
// src/components/Preview/usePreview.ts
const FILE_VIEWER_RENDERER_IDS: readonly string[] = [
  'pdf',
  'office-word-openxml',
  'office-word-binary',
  'open-document',
  'spreadsheet-openxml',
  'spreadsheet-dbf',
  'image',
  'archive' // ← 与包内 file-viewer.capability.json 的 rendererIds 一致
]
```

> 注意：这里填的是 **renderer id**，不是包名，也不是 Vite 里的能力 id。对应关系见 [格式与 renderer 包对照](#格式与-renderer-包对照)，或看包内 `file-viewer.capability.json` 的 `rendererIds`。

**④ 重启 + 验证**

1. **重启 dev**（Vite 插件只在启动/配置变更时生成虚拟模块，热更新不会装配新 renderer）；
2. 必要时清缓存：`rm -rf node_modules/.vite`；
3. 打开该格式：控制台出现新的 `Copied x/y renderer assets`，Network 里能看到 `/file-viewer/vendor/...` 新资源；
4. `npm run build`，确认 `dist/file-viewer/` 多了对应目录，且产物增量符合预期（对着 [为什么改按需装配](#为什么改按需装配体积与启动) 估一下）。

**常见坑**：

- 只改白名单、不改 Vite：组件会判成 `file`，但 bundle 里没有渲染器 → 空态「需要装配预览能力」。
- 只改 Vite、不改白名单：文件仍走 `iframe`，看起来「装了没用」。
- 白名单里写了包内不存在的 id：该扩展名永远判不成 `file`，或渲染时提示找不到 renderer。
- 依赖版本错位（如只 `npm i @file-viewer/renderer-archive` 不锁版本）：可能与 core 的资产版本不一致。

1. **装包**：


3. **白名单加两个 renderer id**：

   ```ts

     'pdf',
     'office-word-openxml',
     'office-word-binary',
     'open-document',
     'spreadsheet-openxml',
     'spreadsheet-dbf',
     'image',
     'office-presentation',
     'office-presentation-binary'
   ]
   ```

4. **重启并验证**：`public/file-viewer/vendor/` 会新增 `pptx/` 与 `ppt/`；打开 `.pptx` 应出现 file-viewer 工具栏，`.ppt` 走旧版运行时。资源会多约 3 MB，产物随之变大。

> 只要 `.pptx`、不要旧 `.ppt`：装 `@file-viewer/renderer-pptx`，Vite 用 `presentation-openxml`，白名单只加 `office-presentation`。

### 用 preset 一次装配

如果一次性要支持一大堆格式，直接换 preset，比逐个装包省事（代价是体积）：

```bash
npm i @file-viewer/preset-standard@3.3.3
```

```ts
// vite/plugins/file-viewer.ts
fileViewerRenderers({
  preset: 'standard', // 或只写 copyAssets，让插件自动发现已安装的 preset
  copyAssets: { baseDir: 'file-viewer' }
})
```

同时把 `usePreview.ts` 的过滤改用 preset 覆盖的能力，例如：

```ts
// 用 preset 后，白名单可以按 preset 实际覆盖的能力整体展开
const FILE_VIEWER_RENDERER_IDS = [
  'pdf', 'ofd',
  'office-word-openxml', 'office-word-binary', 'open-document',
  'spreadsheet-openxml', 'spreadsheet-dbf',
  'office-presentation',
  'archive', 'email',
  'markdown', 'code', 'image', 'video', 'audio'
]
```

> 注意：`preset-standard` 含 `renderer-pptx`（`office-presentation`），`preset-office` 含 `.ppt` + `.pptx`，都会把 PPT 带回来；当前产品取舍是「不预览 PPT」，所以除非确实要恢复 PPT，否则不要整包上 preset。preset 也不含 iWork / CAD/3D / 绘图，需要时按 [格式与 renderer 包对照](#格式与-renderer-包对照) 单独补包 + 补白名单。
>
> 也可以在 `preset` 之外再补 `formats: ['dwg']`，插件会在 preset 基础上追加单条 renderer；但对应的 `@file-viewer/renderer-cad` 仍要自己装。

## 应急与回退

按需装配的故障几乎都集中在「四处不同步」，先按这个顺序确认，再决定是补配置还是整体回退：

| 顺序 | 检查 | 不同步的表现 |
| --- | --- | --- |
| 1 | `package.json` 是否装了对应 `renderer-*` | 启动报 `missingRenderer` 或运行时空态 |
| 2 | `vite/plugins/file-viewer.ts` 是否声明能力 | 包在 `node_modules` 里但没进 bundle |
| 3 | `usePreview.ts` 的 `FILE_VIEWER_RENDERER_IDS` | 声明了能力，但文件仍走 iframe |
| 4 | 是否重启 dev / 清 `.vite` 缓存 | 配置改了不生效 |

### 临时救急：3 分钟加上一种格式

线上反馈某个格式打不开、又来不及走完整评审时，按最短路径处理：

1. `npm i @file-viewer/renderer-<name>@3.3.3`（版本必须与现有 core 一致）；
2. Vite 的 `FILE_VIEWER_RENDERERS` 追加能力 id；
3. `usePreview.ts` 的 `FILE_VIEWER_RENDERER_IDS` 追加 renderer id；
4. 重启 dev（部署则重新 build）；
5. 用该格式的样例文件验证，并顺手确认既有的 PDF / docx / xlsx 没有回归；`.pptx` 仍应走 iframe（PPT 是主动去掉的，不是回归）。

如果只需要**临时**恢复预览、不介意体积，可直接按下一节回退 full 包。

### 回退到 vue3-full

当按需装配出现无法快速定位的问题（例如关键格式白屏、资源 404 排查不完），用下面的完整步骤回到全量包。回退后产物会回到 ≈90 MB、启动重新变慢，属于**应急手段**，问题解决后应按 [新增格式支持](#新增格式支持) 再切回来。

1. **装 full 包**（保留现有 renderer 包不会冲突，但之后可以删）：

   ```bash
   npm i @file-viewer/vue3-full@3.3.3
   ```

2. **组件入口换回 full**：

   ```ts
   // src/components/Preview/previewItem.vue
   // 原：import { FileViewer } from '@file-viewer/vue3'
   import { FileViewer } from '@file-viewer/vue3-full'
   ```

3. **类型判定恢复全量**：

   ```ts
   // src/components/Preview/usePreview.ts
   import { DEFAULT_SUPPORTED_EXTENSIONS, IMAGE_EXTENSIONS } from '@file-viewer/core'

   const SUPPORTED_EXTS: readonly string[] = DEFAULT_SUPPORTED_EXTENSIONS
   // 删掉 DEFAULT_RENDERER_DEFINITIONS 过滤与 FILE_VIEWER_RENDERER_IDS
   ```

4. **Vite 配置简化**（full 自带 `preset-all`，不要再传 `renderers`）：

   ```ts
   export default function createFileViewer() {
     return fileViewerRenderers({
       copyAssets: true
     })
   }
   ```

5. **清理旧产物与缓存**：

   ```bash
   rm -rf public/file-viewer node_modules/.vite
   npm run dev   # full 包会重新复制资源到 public/file-viewer/
   ```

6. **`.gitignore` 检查**：确认仍然忽略 `public/file-viewer/`（回退后是完整的约 200 MB 资源，绝不能提交）。

7. **验证**：PDF / docx / xlsx / 图片各开一个；回退后 PPT 也会重新可用（`preset-all` 含 presentation），可顺带测 `pptx` / `ppt`。Network 里资源路径应为 `/file-viewer/vendor/...`；`npm run build` 后确认 `dist/file-viewer/` 存在。

8. **部署**：整个 `dist` 上线，Nginx 放行 `file-viewer/` 下的 `.wasm`（`application/wasm`）、`.worker.js`、`.mjs`、字体文件；子路径部署确认请求是 `<base>/file-viewer/...`。

9. **切回按需**：按 [四步接入](#四步接入) 恢复 4 个 renderer + 白名单（仍然不含 PPT），然后 `npm uninstall @file-viewer/vue3-full`、`rm -rf public/file-viewer`，重新 build 确认产物体积回到 ≈37 MB 以下。

> 回退前先记一笔当前 `usePreview.ts` 的白名单与 Vite 的 renderer 数组，切回时照抄即可，避免二次排查。

## 与旧版（vue-office）的差异

旧实现（`预览.md` 及 git 历史）基于 `@vue-office/docx` + `@vue-office/excel`，只支持 docx / xls(x) / 图片 / PDF；`.doc` 会进 doc 分支但实际渲染失败，`.ppt` 等走「不支持」空态。2026-11 起 `Preview` 改为 file-viewer。

| 维度 | 旧版（vue-office） | 新版（file-viewer 3.3.3 按需装配） |
| --- | --- | --- |
| 依赖 | `@vue-office/docx`、`@vue-office/excel` | `@file-viewer/vue3` + `core` + `doc` + 4 个 `renderer-*` + `vite-plugin` |
| 支持格式 | docx / xls / xlsx / 图片 / PDF / 其他 iframe | 38 个扩展名（PDF / Word / Excel / 图片），其余 iframe；**PPT 主动不支持** |
| 体积 | ≈ 0.9 MB（压缩后） | ≈ 37 MB（压缩后，去 PPT 前；全量 `vue3-full` 为 ≈ 90 MB） |
| 地址换取 | `readProfileUpload` 内置在 `usePreview` | 抽离为 `resolveUrl` 属性，由消费方提供 |
| 请求库依赖 | `useQuery` + `@tanstack/vue-query` | 无（`useAsyncState`） |
| 组件 props | `minIO` / `download` / `print` / `mode` | `resolveUrl` / `fileName` / `imageViewer` / `toolbar` / `showPrint` / `useBuiltinPrint` |
| 下载 / 打印 | 组件自绘 `PreviewActions.vue`（已删除） | file-viewer 工具栏 + 自定义打印按钮（`#toolbar-end`） |
| 预览类型 | `image \| doc \| xls \| unsupported \| iframe` | `image \| file \| iframe` |
| usePreview 返回 | `resolvedBrowserUrl` / `resolvedOfficeSrc` / `isIframeLoading` / `isOfficeLoading` / `officeErrorMsg` / `excelOptions` / `handlePrint` / `handleDownload` / `fileName` | `ext` / `fileName` / `previewType` / `remoteUrl` / `browserUrl` / `sourceFile` / `isLoading` |
| `.doc` | 不支持 | 支持，且带颜色补丁 |
| 构建 | 无特殊插件 | `fileViewerRenderers({ renderers: [...], copyAssets: { baseDir: 'file-viewer' } })` |
| 静态资源 | 无 | `public/file-viewer/`（dev）→ `dist/file-viewer/`（build），随站点部署 |

- [ ] 从 `package.json` 移除 `@vue-office/docx`（Preview 已不用）；`@vue-office/excel` 若其他报表页面仍在用则保留。

- [ ] `previewItem.vue` 的入口从 `@file-viewer/vue3-full` 改为 `@file-viewer/vue3`。

## 常见问题

**Q1：PDF / Office 白屏，控制台报 Worker 404 或 WASM 加载失败？**

资源没复制或没部署。确认：

1. `vite/plugins/file-viewer.ts` 里 `copyAssets: { baseDir: 'file-viewer' }` 没被删掉；
2. 开发环境启动日志有 `[file-viewer:vite-plugin] Copied x/y renderer assets`，`public/file-viewer/vendor/` 已生成；
3. 生产环境 `dist/file-viewer/` 已随站点部署，且 Nginx 未拦截 `.wasm`（`application/wasm`）、`.worker.js`、`.mjs` 的 MIME 与路径；
4. 子路径部署时请求地址是 `<base>/file-viewer/...`；
5. 目录里如果还有 `vendor/ppt`、`vendor/pptx`、`wasm/cad` 等，说明是切换前残留——清空 `public/file-viewer/` 重新生成。

**Q2：开发时第一次 `npm run dev` 很慢 / 打包后包体巨大？**

本项目已从 `vue3-full` 切到按需装配：资源复制量从 ≈200 MB 降到 ≈12 MB，产物从 ≈90 MB 降到 ≈37 MB（再去掉 PPT 后还会更小）。如果仍然慢或仍然大，按顺序排查：

1. `package.json` 里是否还留着 `@file-viewer/vue3-full` / `preset-all`（会重新装配全量）；
2. `public/file-viewer/` 是否还塞着 full 时代的旧资源——插件只写不删，切换后必须手动清空一次；
3. `node_modules/.vite` 缓存是否还是 full 时代的（`rm -rf node_modules/.vite`）；
4. Vite 插件是否被 `renderers` 之外的东西触发了全量（例如误传 `preset: 'all'`，或装了 `preset-office` 被自动发现）。

**Q3：预览区域高度为 0 / 只看到一条线？**

`preview-content` 需要显式高度。要么保留 `useCalcHeight`，要么按 [4.3 方案 B](#43-usecalcheight) 给 `.preview-content` 设置 `height`（如 `70vh`）。

**Q4：MinIO 地址能取到但预览空白 / 403？**

字符串地址是对象存储的 `relativePath`，浏览器不能直接访问。传 `resolveUrl` 换取签名地址；若已传，检查解析函数返回值是否为空（空串会回退原始地址）。

**Q5：切换文件时重复请求解析接口？**

`resolveUrl` 传了内联箭头函数，每次渲染都是新引用，`watch` 会重新执行。把它定义成 `setup` 顶层的稳定函数。

**Q6：打印按钮不显示？**

三个条件：`showPrint !== false`、`useBuiltinPrint !== true`、当前格式 `availability.print === true`（没有可打印内容的格式会自动隐藏）。

**Q7：点击打印没反应 / 被拦截？**

组件用隐藏 iframe 而非 `window.open`，正常不会被拦截。检查是否有浏览器插件/企业策略禁止 iframe 打印，或 `api.printRenderedHtml` 抛错（此时会有 ElMessage 提示并重新挂载预览）。

**Q8：`.doc` 的彩色字体变成灰色？**

确认复制了 `msDocColors.ts` 并安装了 `@file-viewer/doc`，且文件扩展名确实是 `doc`（不是 `docx`）。补丁只在 `load-complete` 后执行，解析失败会静默。

**Q9：`file-viewer` 的工具栏不想要 / 想加自定义按钮？**

用 `:toolbar="{ download: false }"` 关闭单项；自定义按钮目前不对外暴露插槽，需要直接使用 `@file-viewer/vue3`（装配所需 renderer）的 `#toolbar-end`。

**Q10：想进一步减小体积？**

PPT 已经去掉，剩下的大头是 PDF.js（worker + CMaps + 标准字体 + CJK 兜底字体，约 9 MB）和 Office 解析 Worker / 运行时，这些是格式能力的代价，不能靠调配置消掉。能再压的只有：

- **不要某种格式就删 renderer 包**：例如不预览 Excel，删 `renderer-spreadsheet` 并同步白名单与 Vite 声明，可去掉 `vendor/xlsx/` 与相关 chunk（约 1 MB 资源 + 表格引擎 JS）；
- **清理遗留**：`public/file-viewer/` 里 full 时代残留的 `pptx/`、`ppt/`、`wasm/cad` 等；未使用的 preset；重复的 `@file-viewer/*-full`；
- **确认没有全量**：Vite 的 `renderers` 只写 4 个；`preset` 不要出现。

查看真实构成：

```bash
du -sh dist dist/file-viewer dist/assets
du -sh dist/file-viewer/vendor/*
du -sh dist/assets/* | sort -h | tail -20
```

> `preset-office` 不是「更小的 Office」：它会额外带 `presentation`（PPT 回来）+ `ofd` / `iwork` / `hangul` / `wordperfect`，比手选 4 个 renderer 大得多。

**Q11：pnpm 报找不到 `@file-viewer/vue3/dist/vue3.css`？**

`@file-viewer/vue3` 现在是**直接依赖**（不是 `vue3-full` 的传递依赖），pnpm 严格模式下也能正常解析，不会再出现该报错。若仍报，检查是否还装着 `vue3-full` 并锁定了旧版本。

**Q12：`iframe` 分支的 PDF 显示浏览器自带工具栏，和 file-viewer 不一致？**

PDF 已装配，正常一定走 file-viewer。走 iframe 只有三种可能：`url` 不带扩展名、MIME 与文件头都识别不出类型（见 Q17）、或 `FILE_VIEWER_RENDERER_IDS` 被改坏了。

**Q13：出现「需要装配预览能力」空态？**

说明组件把文件判成了 `file`，但 bundle 里没有对应 renderer——通常是**只改了 `usePreview.ts` 白名单，没装包 / 没改 Vite 声明**。按 [四步接入](#四步接入) 补齐；如果这个格式本来就不打算支持，把它从白名单里删掉，让它回退 `iframe`。

**Q14：新增了 renderer 包，为什么还是走 iframe？**

反向问题：**装了包但没加白名单 / 没重启**。检查 `FILE_VIEWER_RENDERER_IDS` 是否包含该包的 renderer id（不是包名、不是能力 id），然后重启 dev；Vite 插件只在启动时生成装配模块。

**Q15：build 成功但生产环境某些格式打不开，本地正常？**

资源没随站点发布。确认 `dist/file-viewer/` 一起上传、Nginx 对 `.wasm` 返回 `application/wasm`、没有把 `file-viewer/` 当成 SPA 路由回退到 `index.html`（`try_files` 要放行真实文件）。

**Q16：`.pptx` / `.ppt` 打不开，空白或直接下载？**

预期行为，不是 bug。产品确认不预览 PPT：Vite 的 `FILE_VIEWER_RENDERERS` 没有 `presentation`，`usePreview.ts` 白名单也没有 `office-presentation` / `office-presentation-binary`，所以 `.pptx` / `.ppt` 会判成 `iframe`。要恢复请按 [恢复 PPT](#恢复-ppt当前已去掉) 操作；恢复后这两个扩展名会自动回到 `file` 分支。`types.ts` 的 `MIME_EXT_MAP` 里仍保留 `ppt` / `pptx` 映射，它只用于给二进制源推断文件名与扩展名，不会改变预览类型。

**Q17：二进制源（Blob / ArrayBuffer）预览空白，或被 Safari 直接下载？**

多半是 MIME 不可用：没传 `mime`、`Blob.type` 为空、类型是 `application/octet-stream`，或带了 `;charset=` 之类的参数。当前实现会依次处理：

1. 去掉 MIME 参数并转小写，再查 `MIME_EXT_MAP`；
2. MIME 查不到时，动态 `import('file-type')` 按文件头识别（默认取样约 4 KB），能落到预览分支的是 `pdf` / `docx` / `xlsx` / `png` / `jpg` / `gif` / `webp` / `bmp`，再经 `MIME_EXT_MAP` 换算扩展名；
3. 嗅探完成前不创建 blob 地址，避免 Safari 把 MIME 不明的 blob 当下载处理。

补充说明：

- `file-type` 是**动态 import**，只在首次嗅探时加载独立 chunk，不影响首屏；代价是那一次嗅探会多等一个 chunk 加载。
- 用 `file-type` 而不是手写魔数，是因为它维护了完整签名表（含 ZIP 容器内的 OOXML 判定），比逐个 `startsWith` 更不容易漏；动态加载又避免了把整张表塞进主包。
- 识别结果必须能在 `MIME_EXT_MAP` 里找到：`file-type` 能认出但表里没有的（`tiff`、`heic`、`zip`、`mp4`…）仍会回退 `iframe`。
- 旧版 `.doc` / `.xls` / `.ppt` 的 OLE 复合文档只会识别为 `application/x-cfb`，同样不在表里——这类二进制源务必显式传 `mime`。
- SVG 是文本格式，`file-type` 不识别；`pptx` 能识别但 PPT 渲染已去掉，仍为 `iframe`。
- 仍然不行时，请显式传准确的 `mime`，或让后端返回标准 MIME / 先转成 PDF。

**Q18：下载下来的文件名是 UUID / 没有后缀？**

传 `fileName`（业务名称）。组件把它作为 file-viewer 的 `filename`：未带扩展名时按识别结果自动补（`合同` → `合同.pdf`），已带正确后缀则原样使用。注意它只影响下载 / 导出名与二进制 `File` 名，不改变类型判定；图片 / iframe 分支没有组件内下载入口，传了也不会体现在下载上。

## 源码

### `vite/plugins/file-viewer.ts`

```ts
import { fileViewerRenderers } from '@file-viewer/vite-plugin'

/**
 * 项目只预览 PDF / 图片 / Office（Word、Excel），只装配对应 renderer。
 * 使用 @file-viewer/vue3-full / preset-all 会把 30+ 条渲染链路和 200MB+ 资源一起装进来，
 * 导致开发启动变慢、构建产物膨胀，因此这里改为标准包 + 按需 renderer。
 * PPT（.ppt / .pot / .pptx）已确认不需要预览，不再装配 presentation renderer。
 * 新增预览类型时，同时补充本数组与 package.json 中对应的 renderer / assets 包。
 */
const FILE_VIEWER_RENDERERS: readonly string[] = ['pdf', 'word', 'spreadsheet', 'image']

/**
```

```ts
import type { MaybeRefOrGetter } from 'vue'
import type { PreviewProps, PreviewSource, PreviewType } from './types'

import { computed, ref, toValue, watch } from 'vue'
import { useAsyncState, useObjectUrl } from '@vueuse/core'
import { DEFAULT_RENDERER_DEFINITIONS, IMAGE_EXTENSIONS } from '@file-viewer/core'
import { MIME_EXT_MAP } from './types'

/**
 * 已装配的 file-viewer renderer，与 vite/plugins/file-viewer.ts 保持一致。
 * 项目只预览 PDF / 图片 / Office，其余扩展名回退浏览器 iframe，
 * 避免引入全量扩展名后进入「需要装配预览能力」的空态。
 */
const FILE_VIEWER_RENDERER_IDS: readonly string[] = [
  'pdf',
  'office-word-openxml',
  'office-word-binary',
  'open-document',
  'spreadsheet-openxml',
  'spreadsheet-dbf',
  'image'
]

/** 已装配 renderer 覆盖的扩展名（file-viewer 渲染） */
const SUPPORTED_EXTS: readonly string[] = DEFAULT_RENDERER_DEFINITIONS.filter(definition => FILE_VIEWER_RENDERER_IDS.includes(definition.id)).flatMap(
  definition => definition.extensions
)
/** 官方声明支持的图片扩展名（Element 渲染分支使用） */
const IMAGE_EXTS: readonly string[] = IMAGE_EXTENSIONS

/** 是否为二进制源（Blob / ArrayBuffer）*/
const isBinary = (value: unknown): value is Blob | ArrayBuffer => value instanceof Blob || value instanceof ArrayBuffer

/** 去掉 MIME 参数并统一小写：application/pdf;charset=UTF-8 → application/pdf */
const normalizeMime = (value?: string) => value?.split(';')[0].trim().toLowerCase() ?? ''

/** 解析文件扩展名：字符串取地址末段；二进制优先用 mime，其次 Blob 类型 */
const resolveExt = (source: PreviewSource | undefined, mime?: string): string => {
  if (typeof source === 'string') {
    const path = source.split('?')[0]
    const idx = path.lastIndexOf('.')
    return idx > -1 ? path.slice(idx + 1).toLowerCase() : ''
  }
  const candidates = [mime, source instanceof Blob ? source.type : undefined]
  const type = candidates.map(normalizeMime).find(value => MIME_EXT_MAP[value])
  return type ? MIME_EXT_MAP[type] : ''
}

/**
 * 按文件头识别真实类型，用于服务端未返回可识别 MIME 的二进制源（空 / octet-stream / 带参数）。
 * Safari 会把 MIME 无法识别的 blob 地址当下载处理，因此必须尽量识别出真实类型。
 * 动态导入 file-type：只在需要嗅探时加载，不影响首屏体积。
 */
const sniffBinaryExt = async (value: Blob | ArrayBuffer): Promise<string> => {
  const { fileTypeFromBlob, fileTypeFromBuffer } = await import('file-type')
  const type = value instanceof Blob ? await fileTypeFromBlob(value) : await fileTypeFromBuffer(value)
  return type ? (MIME_EXT_MAP[type.mime] ?? '') : ''
}

/**
 * NOTE: file-viewer 支持的类型远多于浏览器内嵌能力，统一优先交由 file-viewer 渲染；
 * 仅图片在 imageViewer='element' 时由 Element 渲染，其余不支持的扩展名回退 iframe。
 * props 可省略：直接 usePreview() 即可只读取预览类型。
 */
export const usePreview = (props: MaybeRefOrGetter<PreviewProps> = {}) => {
  const source = computed(() => toValue(props).url)
  const resolveUrl = computed(() => toValue(props).resolveUrl)
  const mime = computed(() => toValue(props).mime)
  const imageViewer = computed(() => toValue(props).imageViewer ?? 'element')

  /** 源是否为二进制 */
  const isBinarySource = computed(() => isBinary(source.value))

  /** MIME 可直接识别的扩展名 */
  const mimeExt = computed(() => resolveExt(source.value, mime.value))

  /** 文件头嗅探出的扩展名（MIME 不可用时兜底） */
  const sniffedExt = ref('')

  /** 嗅探中：期间不创建 blob 地址，避免 Safari 把未知类型的 blob 直接下载 */
  const isInspecting = ref(false)

  /** 嗅探任务序号：源切换后丢弃过期结果 */
  let inspectId = 0

  watch(
    [source, mime],
    async ([value]) => {
      const id = ++inspectId
      sniffedExt.value = ''

      if (!isBinary(value) || mimeExt.value) {
        isInspecting.value = false
        return
      }

      isInspecting.value = true
      try {
        const next = await sniffBinaryExt(value)
        if (id === inspectId) sniffedExt.value = next
      } finally {
        if (id === inspectId) isInspecting.value = false
      }
    },
    { immediate: true }
  )

  /** 获取文件扩展名 */
  const ext = computed(() => mimeExt.value || sniffedExt.value)

  /** 文件名：优先业务传入的 fileName，其次源地址末段，兜底按扩展名生成（file-viewer 依赖文件名识别类型） */
  const fileName = computed(() => {
    const explicit = toValue(props).fileName
    // 未带扩展名时补上识别出的扩展名，避免下载文件无后缀
    if (explicit) return ext.value && !explicit.toLowerCase().endsWith(`.${ext.value}`) ? `${explicit}.${ext.value}` : explicit
    const value = source.value
    if (typeof value === 'string') {
      const name = value.split('?')[0].split('/').pop()
      if (name?.includes('.')) return decodeURIComponent(name)
    }
    return ext.value ? `预览文件.${ext.value}` : '预览文件'
  })

  /** 预览类型 */
  const previewType = computed<PreviewType>(() => {
    const value = ext.value
    if (imageViewer.value === 'element' && IMAGE_EXTS.includes(value)) return 'image'
    if (SUPPORTED_EXTS.includes(value)) return 'file'
    return 'iframe'
  })

  /** 字符串源地址（二进制源无地址） */
  const sourceUrl = computed(() => (typeof source.value === 'string' ? source.value : ''))

  /** 地址解析：未传 resolveUrl 时原样返回，解析失败回退原始地址 */
  const loadResolvedUrl = async () => {
    const value = sourceUrl.value
    if (!value) return ''
    const resolver = resolveUrl.value
    if (!resolver) return value
    try {
      return (await resolver(value)) || value
    } catch {
      /** 解析失败回退原始地址，由浏览器 / 预览器自行提示 */
      return value
    }
  }

  /**
   * useAsyncState 内部按执行序号丢弃过期结果，无需手写竞态标记；
   * resetOnExecute 保证每次解析前先清空旧地址。
   */
  const { state: resolvedUrl, isLoading, execute: resolveSourceUrl } = useAsyncState(loadResolvedUrl, '', { immediate: false, resetOnExecute: true })

  watch(
    [sourceUrl, resolveUrl],
    ([value]) => {
      if (!value) {
        resolvedUrl.value = ''
        return
      }
      resolveSourceUrl()
    },
    { immediate: true }
  )

  /** 远程地址：字符串源经解析器换取，二进制源无地址 */
  const remoteUrl = computed(() => {
    if (typeof source.value !== 'string') return undefined
    return resolvedUrl.value || undefined
  })

  /** file-viewer 二进制源：补上文件名与类型 */
  const sourceFile = computed<File | undefined>(() => {
    const value = source.value
    if (!isBinary(value) || previewType.value !== 'file') return undefined
    const type = mime.value || (value instanceof Blob ? value.type : '')
    const blob = value instanceof ArrayBuffer ? new Blob([value], { type }) : value
    return new File([blob], fileName.value, { type: type || blob.type })
  })

  /** image / iframe 二进制源的 object URL（useObjectUrl 自动释放） */
  const objectBlob = computed<Blob | undefined>(() => {
    const value = source.value
    if (!isBinary(value) || previewType.value === 'file' || isInspecting.value) return undefined
    return value instanceof ArrayBuffer ? new Blob([value], { type: mime.value ?? '' }) : value
  })
  const objectUrl = useObjectUrl(objectBlob)

  /** 浏览器渲染地址（image / iframe）：解析中先用原始地址占位 */
  const browserUrl = computed(() => {
    if (isBinarySource.value) return objectUrl.value
    return resolvedUrl.value || (typeof source.value === 'string' ? source.value : undefined)
  })

  return {
    /** 文件扩展名 */
    ext,
    /** 下载文件名 */
    fileName,
    /** 预览类型 */
    previewType,
    /** file-viewer 远程地址 */
    remoteUrl,
    /** image / iframe 浏览器地址 */
    browserUrl,
    /** file-viewer 二进制源 */
    sourceFile,
    /** 远程地址解析中 */
    isLoading
  }
}
```

```ts
import type { CharState, MsDocBlock, TableCellBlock } from '@file-viewer/doc'

/** 二进制 .doc 的自定义字符颜色属性（sprmCCv），字节序为 [R, G, B, flag] */
const CUSTOM_COLOR_SPRM = 'sprm_6870'

/** 模型与 DOM 对不齐时，最多向后跳过多少个文本片段再放弃匹配 */
const LOOKAHEAD = 16

/** 渲染顺序上的文本片段及其自定义颜色 */
interface ColoredText {
  text: string
  color?: string
}

/** 读取 run 的自定义颜色；flag 非 0 表示自动色，交给内置调色板 */
const readCustomColor = (style: CharState): string | undefined => {
  const raw = style[CUSTOM_COLOR_SPRM]
  if (!raw || typeof raw !== 'object') return undefined
  const bytes = raw as Record<number, number>
  if (bytes[3] !== 0) return undefined
  const toHex = (value = 0) => value.toString(16).padStart(2, '0')
  return `#${toHex(bytes[0])}${toHex(bytes[1])}${toHex(bytes[2])}`
}

/** 按渲染顺序收集文本片段及其自定义颜色 */
const collectColoredTexts = (blocks: MsDocBlock[]): ColoredText[] => {
  const result: ColoredText[] = []
  const walkCell = (cell: TableCellBlock) => {
    if (cell.hidden) return
    walkBlocks(cell.blocks ?? cell.paragraphs)
  }
  const walkBlocks = (list: MsDocBlock[]) =>
    list.forEach(block => {
      if (block.type === 'table') {
        block.rows.forEach(row => row.cells.forEach(walkCell))
        return
      }
      if (block.type !== 'paragraph') return
      block.inlines.forEach(inline => {
        if (inline.type !== 'text' || !inline.text) return
        result.push({ text: inline.text, color: readCustomColor(inline.style) })
      })
    })
  walkBlocks(blocks)
  return result
}

/** 把 #rrggbb 转成 style.color 的规范化写法，便于和浏览器读回的值比较 */
const toRgb = (hex: string) => {
  const channels = [1, 3, 5].map(index => parseInt(hex.slice(index, index + 2), 16))
  return `rgb(${channels.join(', ')})`
}

/** 未显式设置颜色时，黑色会跟随主题，不需要也不应该回填 */
const isRendered = (element: HTMLElement, color: string) =>
  element.style.color ? element.style.color === toRgb(color) : color === '#000000'

/** 收集渲染出的每一页排版根节点：渲染器默认挂到 Shadow DOM，需要递归穿透 */
const findRoots = (container: HTMLElement): HTMLElement[] => {
  const roots: HTMLElement[] = []
  const walk = (node: ParentNode) => {
    node.querySelectorAll<HTMLElement>('.msdoc-root').forEach(root => roots.push(root))
    node.querySelectorAll<HTMLElement>('*').forEach(element => {
      if (element.shadowRoot) walk(element.shadowRoot)
    })
  }
  walk(container)
  return roots
}

/** 按文本内容顺序把颜色回填到渲染结果上 */
const paintColors = (container: HTMLElement, texts: ColoredText[]) => {
  let cursor = 0
  findRoots(container).forEach(root => {
    const walker = root.ownerDocument.createTreeWalker(root, NodeFilter.SHOW_TEXT)
    let node = walker.nextNode()
    while (node) {
      const textNode = node as Text
      const value = textNode.textContent ?? ''
      const matched = value
        ? texts.findIndex((item, index) => index >= cursor && index < cursor + LOOKAHEAD && item.text === value)
        : -1
      if (matched >= 0) {
        const { color } = texts[matched]
        const element = textNode.parentElement
        cursor = matched + 1
        if (color && element && !isRendered(element, color)) element.style.color = color
      }
      node = walker.nextNode()
    }
  })
}

/**
 * NOTE: 修复二进制 .doc 的字体颜色。
 * file-viewer 的 msdoc 渲染只支持 16 色调色板：解析层虽然把 sprmCCv（自定义 RGB）
 * 原样放进了字符样式（sprm_6870），但渲染层只读取 colorIndex，自定义颜色会退化成灰色；
 * 这里重新解析文件，按文本顺序把颜色回填到 DOM。
 *
 * 颜色问题调研结论（@file-viewer/doc 3.3.3，当前最新版本）：
 * 1. 官方方案：无。MsDocRenderOptions 只有 css / reviewMode / externalLinkPolicy /
 *    externalResourcePolicy，没有颜色映射或调色板扩展配置，也无相关修复版本。
 * 2. 可直接使用的流行方案：无。浏览器端没有其他能渲染二进制 .doc 的流行 npm 包
 *    （mammoth、docx-preview 等只支持 .docx）；服务端 LibreOffice 转 PDF/HTML 属于
 *    架构改造，不是可直接使用的补丁。
 * 因此保留此补丁。
 */
export const repairMsDocColors = async (container: HTMLElement, source: File | string) => {
  const { parseMsDoc } = await import('@file-viewer/doc')
  const buffer = typeof source === 'string' ? await (await fetch(source)).arrayBuffer() : await source.arrayBuffer()
  const model = await parseMsDoc(buffer)
  paintColors(container, collectColoredTexts(model.blocks))
}
```
