---
title: "后端学习规划（岗位对齐）"
---

> 适用对象：以 Node.js 入门后端，目标达到企业初级/中级后端要求。
>
> 使用方式：按阶段推进，每个阶段必须有**可运行的产物**和**可验证的验收证据**。没有产物就不算学完。
>
> 相关文档：[学习路线](../../前端/node/学习路线.md)、[后端技能地图与岗位对照](./后端技能地图与岗位对照.md)、[练手项目](../../前端/node/实战/练手项目.md)。

## 1. 总览

| 阶段 | 目标 | 核心内容 | 产物 | 通过标准 |
| --- | --- | --- | --- | --- |
| S0 准备 | 工具与环境就绪 | Git、HTTP、SQL、Node 环境 | 可运行的空项目 | 能独立启动服务与数据库 |
| S1 能写 | 达到初级后端 | 异步、HTTP、Express 分层、SQL 基础、测试 | 项目 A：TODO API | 评分 ≥3，测试全绿 |
| S2 能上线 | 达到中级后端 | SQL 优化、Redis、队列、可观测性、部署 | 项目 B：通知/订单服务 | 评分 ≥4，压测与回滚通过 |
| S3 能设计 | 达到中高级 | NestJS、系统设计、安全评审、协作 | 项目 C：企业级模块 + 设计文档 | 评分 ≥4，设计评审通过 |
| S4 深耕 | 方向选择 | 实时、搜索、微服务、Serverless 等 | 一个深度项目 | 能讲清取舍与故障处理 |

时间可灵活调整，但**顺序不要跳**：SQL、测试、部署这三项是后续所有内容的地基。

## 2. S0 准备（约 1 周）

### 学习步骤

1. 安装 Node 20/22 LTS，确认 `node -v`、`npm -v`；
2. 安装 PostgreSQL（或用 Docker），能执行 `psql`；
3. 熟悉 Git：分支、提交、合并、回滚；
4. 复习 HTTP：方法、状态码、Header、Cookie；
5. 建一个空项目：`npm init -y`，写一个 `/health` 接口。

### 验收标准

- [ ] 能用一个命令启动数据库并连接成功
- [ ] 能用 `curl` 调通自己的 `/health`
- [ ] 能解释 200/201/204/301/400/401/403/404/422/500 的使用场景
- [ ] Git 能完成一次分支开发 + 合并

## 3. S1 能写（约 4–6 周）

### 3.1 学习步骤

| 顺序 | 主题 | 具体动作 | 对应文档 |
| --- | --- | --- | --- |
| 1 | 运行时与异步 | 写 5 个小脚本验证事件循环、并发池、错误处理 | [事件循环与异步](../../前端/node/基础/事件循环与异步.md) |
| 2 | 文件与流 | 写一个日志统计 CLI，处理 100MB 文件 | [Stream、Buffer 与文件](../../前端/node/基础/Stream、Buffer与文件.md) |
| 3 | HTTP 基础 | 用 `node:http` 实现 3 个接口 | [HTTP 与 REST](./HTTP与REST.md) |
| 4 | Express 分层 | 按 route/controller/service/repository 重构 | [Express 项目规范](./Express项目规范.md) |
| 5 | SQL 基础 | 建 3 张表，写 10 条查询，理解索引与事务 | [数据库设计与查询优化](./数据库设计与查询优化.md) |
| 5.5 | ORM/Prisma | 用 Prisma 建模型、迁移、CRUD、事务与分页 | [Prisma 数据访问与迁移](./Prisma数据访问与迁移.md) |
| 6 | 测试 | 用 `node:test` + supertest 覆盖关键接口 | [Node 后端测试与可观测性](./Node后端测试与可观测性.md) |

### 3.2 项目 A：TODO API

要求：

- 注册、登录、退出；
- TODO 增删改查、分页、按状态过滤；
- 每个用户只能访问自己的数据；
- 统一错误结构、参数校验；
- 接口测试覆盖成功/未登录/无权限/参数错误/不存在；
- README + 接口表 + `.env.example`。

### 3.3 验收标准

- [ ] 至少 8 个接口，状态码符合 REST 约定
- [ ] 参数错误返回 422，未登录 401，越权 403/404
- [ ] 至少 15 个接口测试，全部通过
- [ ] `docker compose up` 能启动 API + 数据库
- [ ] 数据库有索引，列表查询不走全表扫描
- [ ] 仓库无明文密钥，日志不含密码
- [ ] 按评分表自评 ≥3 分（见[练手项目](../../前端/node/实战/练手项目.md)）

### 3.4 考核点

**口述**

- `setTimeout`、`Promise.then`、`await` 的执行顺序；
- 为什么用连接池，连接数设多少；
- 事务的 ACID 与隔离级别；
- Session 与 JWT 的取舍。

**实操（限时）**

1. 新增一个接口并补测试；
2. 给一个慢查询加索引，用 `EXPLAIN` 说明前后差异；
3. 找出代码中的 SQL 注入并修复；
4. 解释一次 401 与 403 的排查过程。

## 4. S2 能上线（约 4–6 周）

### 4.1 学习步骤

#### ① SQL 深化

- 执行计划：`EXPLAIN ANALYZE`，识别全表扫描、回表、临时表；
- 索引：联合索引最左前缀、覆盖索引、区分度；
- 分页：深分页改 keyset（`where id > ?`）；
- 迁移：用 migration 管理表结构，禁止手改生产库；
- 连接池：最大连接、超时、慢查询日志。

#### ② Redis 与缓存

参考：[Node 后端缓存、队列与幂等](./Node后端缓存、队列与幂等.md)。

- 缓存模式：cache-aside、读写穿透；
- 失效：TTL + 随机抖动，避免同时过期；
- 三大问题：穿透（空值缓存/布隆过滤器）、击穿（互斥重建）、雪崩（打散过期）；
- 分布式锁：`SET NX PX` + 唯一 value + Lua 释放；
- 会话、限流、排行榜等典型用法。

#### ③ 消息队列

- BullMQ：入队、消费、并发、重试、退避；
- 失败处理：重试次数、死信队列、人工补偿；
- 幂等消费：业务唯一键 + 唯一索引；
- 可靠性：先落库再发消息，必要时用 outbox；
- 顺序与重复：不要假设消息只来一次、只来一遍。

#### ④ 可观测性

- 日志：pino + request id，结构化字段；
- 指标：请求量、错误率、P95 延迟、队列积压、缓存命中率；
- 链路：OpenTelemetry，至少串起「入口 → 数据库 → 外部调用」；
- 告警：错误率、延迟、队列深度、磁盘/连接数；
- 排障顺序：看指标 → 看日志 → 看链路 → 复现。

#### ⑤ 部署与发布

- Docker 多阶段构建，非 root 运行；
- Nginx：反向代理、gzip、超时、限流、HTTPS；
- CI：安装 → 测试 → 构建 → 部署；
- 优雅退出与健康检查；
- 回滚：镜像版本回退，数据库迁移可回退。

### 4.2 项目 B：通知/订单服务

要求：

- 创建任务接口支持 `Idempotency-Key`，重复请求返回同一结果；
- 第三方回调验签、防重放、幂等；
- 耗时任务入队，worker 消费并更新进度；
- 热点数据走 Redis 缓存，缓存失效有保护；
- 暴露 `/metrics` 与 `/health`；
- 有压测脚本与基线记录。

### 4.3 验收标准

- [ ] 重复回调只产生一条业务记录
- [ ] 100 个并发请求同时未命中缓存时，只有 1 次回源
- [ ] 失败任务重试 3 次后进入死信，可手动重放
- [ ] 压测报告包含 RPS、P95、错误率、CPU/内存
- [ ] 能在 5 分钟内完成一次版本回滚
- [ ] 一次请求可在日志/链路中完整串起来
- [ ] 评分表 ≥4 分

### 4.4 考核点

**设计题**

- 缓存 key 怎么设计，数据更新时如何失效；
- 消息重复消费会怎样，如何保证幂等；
- 订单创建与扣库存如何保证一致性；
- 队列积压如何定位与扩容。

**实操**

1. 用 `EXPLAIN` 优化一条慢查询；
2. 模拟缓存击穿，验证互斥重建生效；
3. 杀掉 worker，验证任务不丢；
4. 制造一次 500，要求 10 分钟内定位根因。

## 5. S3 能设计（约 4–6 周）

### 5.1 学习步骤

#### ① NestJS 与模块化

- Module / Provider / DI / Pipe / Guard / Interceptor / Filter；
- 按业务域拆分模块，禁止跨模块访问 repository；
- 全局校验、统一异常、统一响应；
- Swagger、健康检查、日志、测试；
- 参考[NestJS 企业级实践](./NestJS企业级实践.md)。

#### ② 系统设计

固定分析顺序：

```text
需求与约束 → API 契约 → 数据模型 → 一致性方案
→ 失败场景 → 容量估算 → 监控与回滚
```

必须掌握的模式：

- 幂等：唯一键、幂等表、状态机；
- 最终一致：本地消息表 / outbox、补偿；
- 分布式事务：优先避免，必要时 Saga；
- 限流与降级：令牌桶、熔断、排队；
- 容量：QPS、连接数、存储增长、峰值倍数。

#### ③ 安全评审

按 OWASP 逐项检查：注入、越权、认证、敏感数据、XXE、SSRF、依赖漏洞、日志泄露。

#### ④ 协作与交付

- 接口契约：OpenAPI 先行的联调方式；
- Code Review：看边界、错误处理、SQL、日志、测试；
- 文档：README、ADR（架构决策记录）、故障复盘；
- 需求拆解：把一句话需求拆成接口、表、任务与验收。

### 5.2 项目 C：NestJS 企业级模块

要求：

- 独立业务模块（通知/审计/订单任选）；
- 全局校验、异常、响应格式统一；
- JWT + 角色 + 资源归属；
- Swagger、健康检查、结构化日志；
- 单元测试 + e2e；
- 一页系统设计文档：目标、约束、方案对比、失败场景、监控。

### 5.3 验收标准

- [ ] 模块无循环依赖，边界清晰
- [ ] OpenAPI 可直接联调
- [ ] 单测 + e2e 全绿
- [ ] 设计文档通过一次同行评审
- [ ] 能画出请求链路并指出单点
- [ ] 评分表 ≥4 分

### 5.4 考核点

**白板设计**

设计一个「下单 + 扣库存 + 支付回调」系统：

- 如何防重复下单；
- 超卖如何避免；
- 回调重复/乱序如何处理；
- 数据库挂了怎么办；
- 峰值 10 倍流量如何应对。

**代码评审**

给出一段有 3 个问题的代码（SQL 注入、越权、无超时），要求在 15 分钟内指出并说明修复方案。

## 9. 常见偏差

| 偏差 | 后果 | 纠正 |
| --- | --- | --- |
| 只看不写 | 面试说不出细节 | 每个概念必须有可运行代码 |
| 追框架不学基础 | 换框架就废 | 先手写 HTTP/SQL，再上框架 |
| 跳过 SQL | 无法定位性能问题 | 每阶段都练 `EXPLAIN` |
| 不做测试 | 不敢改代码 | 接口测试先于重构 |
| 不做部署 | 不知道线上会发生什么 | 至少完整部署一次 |
| 只学 Node 专属 | 换语言从零开始 | 优先掌握通用后端能力 |
| 项目贪多 | 每个都半成品 | 一个项目做到能上线再加下一个 |
