---
title: "Node 系统设计与协作交付"
---

> 从“能写接口”到“能负责一个模块”，需要系统设计能力，也需要接口契约、评审、发布和故障处理这些协作交付能力。本文给出可执行的清单。

## 1. 设计从边界开始

写代码前先回答：

- 这个模块负责什么，不负责什么；
- 谁是调用方，同步还是异步；
- 数据所有权归谁；
- 失败时调用方看到什么；
- 哪些操作必须幂等；
- 峰值 QPS、数据量、延迟目标。

画一张最小架构图：

```text
Client -> API -> Service -> DB
                  |-> Redis
                  |-> Queue -> Worker -> Third-party
```

## 2. API 契约

- 用 OpenAPI 描述路径、参数、响应、错误码；
- 错误响应统一结构：

```json
{
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "订单不存在",
    "requestId": "..."
  }
}
```

- 版本化：URL（`/v1`）或 header；
- 分页统一 cursor/limit；
- 时间统一 ISO8601 UTC；
- 金额统一整数分/字符串，不用浮点；
- 幂等写接口要求 `Idempotency-Key`；
- 不要随意改字段含义，废弃字段先标记再移除。

## 3. 一致性与事务边界

- 单库单事务能保证的，不要引入分布式事务；
- 跨服务用 outbox + 最终一致；
- 读多写少可以缓存，但明确过期和失效；
- 关键状态用状态机，禁止任意跳转；
- 唯一约束是最后一道幂等防线。

## 4. 容量与性能

- 估算 QPS、平均/峰值、数据增长；
- 接口 P95 目标写进验收；
- 数据库连接数 = 实例数 × pool；
- 热点数据缓存，慢查询加索引；
- 大文件/导出走异步任务；
- 压测要覆盖峰值和降级。

## 5. 失败设计

- 超时、重试、退避、熔断；
- 重试必须幂等；
- 第三方失败不能拖垮主流程；
- 降级返回可接受的旧数据/默认值；
- 死信队列 + 人工补偿；
- 每个外部依赖有超时和隔离。

## 6. 可观测性设计

- 请求 id/trace id 贯穿；
- 关键业务事件结构化日志；
- 指标：请求、错误、延迟、队列、缓存、连接池；
- 告警基于症状，有 runbook；
- 发布后观察窗口和回滚条件。

## 7. 评审清单

### 设计评审

- [ ] 边界、数据所有权清楚；
- [ ] API 契约和错误码明确；
- [ ] 幂等、事务、一致性方案；
- [ ] 容量、延迟、降级；
- [ ] 安全与权限；
- [ ] 迁移与回滚；
- [ ] 监控、日志、告警。

### Code Review

- [ ] 输入校验、权限、资源归属；
- [ ] SQL/ORM 查询是否有索引、N+1；
- [ ] 事务范围和外部调用；
- [ ] 错误处理不吞异常；
- [ ] 日志不泄露敏感信息；
- [ ] 测试覆盖关键分支；
- [ ] 配置/密钥不硬编码。

## 8. 交付流程

```text
需求澄清 -> 设计/契约 -> 开发 -> 自测 -> 评审
-> 集成测试 -> 灰度 -> 全量 -> 观察 -> 复盘
```

- 需求拆成可验收的小项；
- 接口先定契约，前后端并行；
- 数据库迁移先于代码兼容；
- 发布前准备回滚脚本；
- 发布后看指标，不只看日志。

## 9. 值班与故障

- 有 on-call 和升级路径；
- 告警有负责人、阈值、runbook；
- 故障时先止损：限流/降级/回滚；
- 记录时间线、影响面、根因；
- 复盘输出改进项、负责人、截止时间；
- 同类故障要有自动化防护。

## 10. 技术文档

- ADR：为什么选这个方案，替代方案是什么；
- 接口文档：OpenAPI；
- 运行手册：启动、配置、迁移、回滚、常见故障；
- 数据字典：表、字段、枚举、敏感级别；
- 变更记录：迁移、配置、依赖升级。
