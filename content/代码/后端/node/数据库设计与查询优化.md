> 数据库是 Node 后端从“能写接口”到“能上生产”的分水岭。本文覆盖建表、索引、SQL、事务、分页、慢查询与迁移，示例以 PostgreSQL 为主。
>
> ORM 用法见[Prisma 数据访问与迁移](./Prisma数据访问与迁移.md)。

## 1. 建表先想清楚

### 1.1 主键与外键

```sql
CREATE TABLE users (
  id          text PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  name        text,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE posts (
  id          text PRIMARY KEY,
  author_id   text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title       text NOT NULL,
  content     text,
  published   boolean NOT NULL DEFAULT false,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

原则：

- 主键用稳定、不可变的 ID（cuid/uuid/雪花）；
- 外键列必须有索引，否则关联查询和删除会全表扫描；
- 时间用 `timestamptz`，不要用字符串；
- 金额用 `numeric` 或整数分，不要用浮点。

### 1.2 范式与反范式

- 先按第三范式拆表，避免重复数据；
- 读多写少、统计频繁时可以冗余字段（如 `comment_count`），但要有更新策略；
- 不要为了“以后可能”过度设计表；
- 多态关联、EAV 表通常先别用，优先显式表。

## 2. 索引

### 2.1 常用索引

```sql
-- 单列
CREATE INDEX idx_posts_author ON posts(author_id);

-- 复合索引：最左前缀
CREATE INDEX idx_posts_author_created ON posts(author_id, created_at DESC);

-- 唯一
CREATE UNIQUE INDEX uq_users_email ON users(lower(email));

-- 部分索引
CREATE INDEX idx_posts_published ON posts(created_at DESC) WHERE published = true;
```

### 2.2 索引设计规则

1. 先看查询条件、排序、连接字段；
2. 复合索引顺序按“等值 → 范围 → 排序”；
3. 区分度低的字段（性别、状态）单独建索引收益小；
4. 写多读少的表少建索引；
5. 用覆盖索引减少回表；
6. 索引也会占空间、拖慢写入，必须用 `EXPLAIN` 验证。

### 2.3 索引失效

- 对索引列做函数/表达式（`where lower(email)=...`）要用表达式索引；
- 隐式类型转换；
- `LIKE '%xx'` 前缀通配；
- `OR` 条件没有合适索引；
- 统计信息过期，需要 `ANALYZE`。

## 3. 查询与 EXPLAIN

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title, created_at
FROM posts
WHERE author_id = $1 AND published = true
ORDER BY created_at DESC
LIMIT 20;
```

看什么：

- 是否走 `Seq Scan`（大表通常不好）；
- `rows` 估算与实际差多少；
- `actual time` 哪一步最慢；
- 是否发生外部排序/临时文件；
- `Buffers` 的 shared read 是否过高。

常见优化：

```sql
-- 分页 + 排序走复合索引
CREATE INDEX idx_posts_author_pub_created
  ON posts(author_id, published, created_at DESC);
```

- 只 select 需要的列；
- 避免 `SELECT *`；
- 避免 N+1，用 join/批量查询；
- 大批量写用 `COPY`/批量 insert，不要逐条。

## 4. 分页

### 4.1 Offset 分页

```sql
SELECT id, title FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;
```

问题：深分页越翻越慢，数据变化会漂移。适合后台小数据量。

### 4.2 Cursor 分页

```sql
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- 需要稳定排序（时间 + id）；
- 适合信息流、列表、API；
- 返回 `nextCursor`，不返回总数（或另做近似统计）。

## 5. 事务与锁

```sql
BEGIN;
UPDATE inventory SET stock = stock - 1 WHERE product_id = $1 AND stock > 0;
INSERT INTO orders (id, product_id, user_id) VALUES ($1, $2, $3);
COMMIT;
```

- 事务要短，不要在事务里调用外部 HTTP；
- 用唯一约束/条件更新实现幂等；
- 高并发扣减用 `UPDATE ... WHERE stock > 0`，不要先查再改；
- 理解隔离级别：Read Committed 是 PostgreSQL 默认；
- 死锁：固定加锁顺序、减少事务范围、重试。

## 6. 迁移

- 迁移脚本必须版本化；
- 生产用 `prisma migrate deploy` 或等价工具；
- 大表加索引用 `CREATE INDEX CONCURRENTLY`（不在事务内）；
- 加非空列分三步：加可空列 → 回填 → 加非空约束；
- 删除列前先停止读写并备份；
- 迁移前备份，迁移后校验行数/关键字段。

## 7. 连接池

- Node 进程复用连接池，不要每请求新建；
- 连接数 = 实例数 × pool size，不能超过数据库上限；
- 事务占用连接，慢查询会拖垮池；
- Serverless 用 PgBouncer/代理，避免连接风暴；
- 监控 `pg_stat_activity` 的等待和长事务。

## 8. 备份与恢复

- 每日全量 + 持续 WAL 归档；
- 定期做恢复演练，不能只看备份成功；
- 迁移前手动快照；
- 误删/误更新要有 PITR（按时间点恢复）。

## 9. 检查清单

- [ ] 外键有索引；
- [ ] 列表排序有复合索引；
- [ ] 关键查询用 `EXPLAIN ANALYZE` 验证；
- [ ] 没有 N+1；
- [ ] 深分页用 cursor；
- [ ] 事务短、无外部调用；
- [ ] 迁移可重复、可回滚/可向前修复；
- [ ] 连接池与数据库上限匹配；
- [ ] 有备份和恢复演练。
